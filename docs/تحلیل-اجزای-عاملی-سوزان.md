# تحلیل عمیق ۶ مؤلفهٔ عاملی (Agentic) در سوزان

تاریخ بررسی: ۱ اکتبر ۲۰۲۶ · شاخه: `claude/gifted-feynman-kmtdxv` · مخزن: `ariaspring46/sozan-core`

این سند نتیجهٔ خواندن مستقیم کد است، نه حدس از روی مستندات. هر ادعا با مسیر فایل و (در جاهای مهم) شمارهٔ خط آمده است. جاهایی که فقط «برنامه» است و در کد نیست، جدا مشخص شده‌اند. واحد بررسی، ۶ مؤلفه‌ای است که خواسته شد: **حلقه، ابزارها، کانتکست، محیط، حافظه، مشاهده‌پذیری**.

> **اصلاح نسبت به گزارش اول در چت.** در بررسی عمیق‌تر سه چیز روشن‌تر شد: (۱) عامل پنجمی هم هست: **خط تلفن (`voice-gateway/`)**؛ (۲) ابزار پایش (`tools/monitor`) در این شاخه نیست ولی طبق گزارش‌های `storefront-talk.md` روی شاخهٔ دیگری ساخته و روی ماشین خانه اجرا می‌شود، پس «پیاده نشده» نادرست بود؛ (۳) حافظهٔ مشتری در عمل در تولید هیچ‌وقت نوشته نمی‌شود (بخش ۵ و یافتهٔ F7).

## ۰) نقشهٔ کلی

سوزان یک «عامل واحد» نیست. پنج عامل جدا دارد که هرکدام الگوی متفاوت و سطح اختیار متفاوتی دارند:

| # | عامل | فایل اصلی | الگو | چه کسی تصمیم می‌گیرد |
|---|---|---|---|---|
| A | **روتر چت پنل** | `services/router_service.py` (۱۸۷۰ خط) | یک‌گذر (single-shot): دروازهٔ قاعده‌ای ← انتخاب ابزار با مدل ← بردار نجات | مدل فقط *نام ابزار* را می‌گزیند |
| B | **عامل دایرکت (فروشنده)** | `services/inbox_agent_service.py` (۱۲۹۴ خط) | حلقهٔ واقعی ابزار، حداکثر ۴ دور | مدل ابزار را صدا می‌زند و جواب می‌سازد؛ گاردها بعدش |
| C | **ویرایشگر فروشگاه + کارخانهٔ سایت** | `shop_edit_service.py`، `shop_service.py`، `shop_edit_verify.py` | حلقهٔ اکشن: snapshot ← اجرا ← بررسی ← rollback | classifier قاعده‌ای؛ مدل فقط وقتی `edit_llm` باشد |
| D | **استودیو (کپشن و تصویر و ویدیو)** | `studio_chat_service.py`، `studio_compose_service.py`، `image_provider_service.py`، `worker.py` | پایپ‌لاین با تلاش مجدد + کار پس‌زمینه + گارد بینایی | مدل JSON می‌دهد؛ کد پاک‌سازی و اعتبارسنجی می‌کند |
| E | **عامل تلفن** | `voice-gateway/` (~۸٬۵۰۰ خط) | حلقهٔ تماس زنده: STT ← برنامهٔ نوبت (`plan_turn`) ← LLM یا جملهٔ ثابت ← TTS | ماشین حالت `SalesState`؛ مدل فقط وقتی `kind="model"` |

اصل طراحی مشترک: **اول قاعده‌های قطعی، بعد مدل، بعد گاردهای خروجی.** مدل هرگز مستقیم روی دنیا اثر نمی‌گذارد؛ هر اثر از یک تابع از پیش نوشته‌شده می‌گذرد. این انتخاب آگاهانه است و دلیلش در کد دیده می‌شود: مدل‌های محلی/ارزان، فارسی، و هزینهٔ اشتباه بالا (انتشار پست، پرداخت، تغییر سایت زنده).

## ۱) حلقه (The Loop)

### ۱.۱ حلقه‌های زیرساختی (`main.py`)

| حلقه | دوره | رفتار در خطا |
|---|---|---|
| `_channel_poll_loop` | ۴ ثانیه (تأخیر اول ۴ث) | `CancelledError` عبور می‌کند، سایر خطاها `log.exception` و ادامه. در `channel_poll_service`: بعد از ۳ شکست متوالی، ۳۰۰ث backoff؛ فاصلهٔ حداقل اینستاگرام ۳۰ث |
| `_housekeeping_loop` | ۶۰ ثانیه (تأخیر اول ۲۰ث) | روی همهٔ مستأجرها: `expire_stale` (کمپین استودیو) و `expire_stale_sending` (ارسال‌های بیش از ۱۲۰ث) |
| `_rearm_inbox` | یک‌بار، هنگام بالا آمدن | پاسخ‌های خودکار نیمه‌کاره بعد از ری‌استارت دوباره فعال می‌شوند |
| `renewal_reminder_service.loop` | پس‌زمینه | یادآوری تمدید |
| `llm_routing_service.refresh_loop` | ۳۰ ثانیه | `GET {observe}/observe/api/routing`؛ در خطا از `llm-routing.json` روی دیسک می‌خواند و یک‌بار رویداد `routing-stale` می‌فرستد |
| `loop_watch` | ضربان ۱ث | thread مستقل هر ۵ث؛ اگر event loop بیش از ۵ث نزده باشد `faulthandler.dump_traceback(all_threads)` و حداکثر هر ۳۰ث |
| `worker.py` | `BRPOP` با timeout ۵ث | پروسهٔ جدا برای کار استودیو؛ خطا ← پیام ناموفق روی همان حباب چت |

`lifespan` در شروع `_security_guard()` را اجرا می‌کند (کلید JWT نمونه/کوتاه‌تر از ۳۲ نویسه یا `OTP_DEV` همراه `PAYMENTS_ENABLED` ← بالا نمی‌آید) و `router_service.clear_dead_busy()` را (قفل‌های نوبت که پروسه‌شان مرده است پاک می‌شود).

**نکتهٔ طراحی:** کارهای سنگین استودیو فقط وقتی `SOZAN_WORKER=1` باشد به صف Redis (`sozan:studio-jobs`) می‌روند (`router_service.py:1326`، `studio_chat_service.py:1401`، `job_queue.py`). `deploy-api.sh` این متغیر را با drop-in برای `sozan-api` می‌گذارد و `sozan-worker.service` را فعال می‌کند (`MemoryMax=3G`). بدون آن، استودیو درون همان پروسهٔ API اجرا می‌شود.

### ۱.۲ عامل A — روتر (`router_service.turn` خط ۱۶۱۶، `_execute` خط ۱۶۶۰)

روتر **حلقهٔ ReAct نیست**. هر نوبت دقیقاً یک بار به مدل می‌رود و نتیجهٔ ابزار هرگز به مدل برنمی‌گردد.

```
POST /chat  (idempotency + body stamp)
 └─ turn():
     1. _bind_thread → _claim_turn(key)           # فایل router[-tid]-busy.json {token,pid,until=now+20s,key}
        ├─ اگر زنده بود → RouterBusy → API منتظر کش idempotency می‌ماند (حداکثر 40×0.5s)
        └─ _heartbeat هر 8s → _touch_turn
     2. _execute():
        a. cancel_id/confirm_id مطابق کارت باز؟ → اجرا/لغو کارت (+ _reject_write)
        b. کارت منقضی (CARD_TTL=24h)؟ → «کارت قبلی منقضی شد»
        c. _over_daily_cap (80 نوبت / 12000 توکن تکمیل) → «برای امروز کافی است»
        d. decide():
             direct → _direct_reply (_fact_reply: ~25 topic قطعی، continue، زبان، capability...)
             tool   → route_tool (قاعده: build/rebuild/publish/catalog_add/edit/advice/studio)
             model  → ادامه
        e. اگر کارت باز و پیام «وضعیت/صندوق/خوانده» نیست → HOLD_PENDING
        f. model: complete_tools([system,user], TOOLS)   # max_tokens=150, timeout=45
        g. calls خالی؟ → _force_shop_build؟ وگرنه router_embed.rescue_tool (کسینوس ≥ 0.75)
           وگرنه refusal ثابت یا متن مدل + fallback_tally.note("fallback")
        h. _choose_call (رتبه: نوشتنی 0 < shop_chat 1 < ask_user 2 < خواندنی 3)
        i. گاردها: _never_tool → ALLOWED → _reject_write → _stamp_content_id → _authority_route → HOLD_PENDING
        j. WRITE_TOOLS (یا shop_chat با «از نو») → کارت تأیید (summary + pending 24h) ← پایان نوبت
        k. ask_user → سؤال ساخت‌یافته؛ وگرنه _run_tool → _guard_reply → snapshot
     3. _flush_trace → router-turns.jsonl
     4. finally: beater.cancel(); _release_turn(token)
```

نکات دقیق:

- **سه مسیر ورود به ابزار:** دروازه (`path=gate`)، مدل (`path=model`)، بردار (`router-embed-rescue`). همهٔ سه در `_trace` ثبت می‌شوند.
- **قفل نوبت** بین پروسه‌ای است (فایل + `os.kill(pid,0)`)، نه `asyncio.Lock`. تابع `turn_lock()` (خط ۲۴۱) در مخزن تعریف شده ولی **هیچ‌جا استفاده نمی‌شود** (کد مرده).
- اگر `_run_tool` استثنا بدهد، فقط پیام فارسی امن می‌رود؛ متن‌های دارای مسیر/URL/traceback فیلتر می‌شوند (`_UNSAFE_ERROR`).
- `router_spec.json` یک ماشین حالت (`idle/built/card_open/composing`) تعریف می‌کند و `turn_parse.spec_state/spec_note` برای آن هست، ولی **هیچ کد تولیدی آن‌ها را صدا نمی‌زند** (فقط تعریف‌اند). منطق حالت‌ها عملاً با `if`های پراکنده در `_route_shop` و `_authority_route` پیاده شده است.

### ۱.۳ عامل B — دایرکت (`inbox_agent_service._answer` خط ۱۱۰۰)

این تنها حلقهٔ واقعیِ «مدل ← ابزار ← مدل» در بک‌اند است.

```
answer(text, thread, source)
 └─ _answer():
     ① _policy_reply   (sales-policy.json: ارسال/مرجوعی/ساعت... بدون مدل)
     ② _known_reply    (پاسخ قطعی از کاتالوگ/سفارش، بدون مدل)
     ③ messages = [system, history(12×240), user]
        اگر مشتری کالایی نام برد و خرید صریح نخواسته: _seed_stock (موجودی از قبل تزریق)
     ④ while rounds < MAX_ROUNDS(4) or force_retry:      # حداکثر 5 دور با retry اجباری
          left = INBOX_TURN_BUDGET(30s) - elapsed → اگر < 1: hand-off «مهلت مدل»
          text, calls = _complete(messages, tools)       # زنجیرهٔ ابر→ابر→محلی، هر hop ≤ 15s
          اگر calls خالی:
              • بدون ابزار و بدون عدد پایه‌دار و موضوع قیمت/موجودی؟ → یک بار nudge با intent_hint (بردار) و continue
              • _numbers_ok(reply, tool_blob)  ← عددِ بی‌منبع؟ یک بار retry، بعد hand-off
              • _fix_links → _claims (مدل دوم، فقط اگر ادعای کیفی ولی غیرموجود در facts)
              • بازگشت reply[:1000]
          وگرنه: هر call را اجرا و نتیجه را به‌صورت role=tool به messages اضافه
              payment_link بدون خرید صریح → ok:false بدون اجرا
              خطای ابزار → hand-off
     ⑤ پایان دورها → hand-off «دورها تمام شد»
```

شرط‌های خروج (همه رویداد `inbox-agent` با `status` و `reason` می‌فرستند): جواب نهایی، «مهلت مدل»، «خطای ابزار»، «خطای ابزار پرداخت»، «عدد نامجاز»، «جواب خالی»، «دورها تمام شد». **hand-off** یعنی جملهٔ ثابت «همکارم به‌زودی جواب می‌دهد» و علامت‌گذاری نخ برای فروشنده.

حلقهٔ بیرونی صندوق (`inbox_service.maybe_auto_reply`): حالت‌ها `""`/`draft`/`send` از پلن می‌آید؛ فاصلهٔ ۴۵ث بین پاسخ‌ها (`AUTO_GAP_SEC`)؛ حداکثر ۲۰ ارسال خودکار در ساعت برای هر نخ؛ `AUTO_RETRY_MAX=2`؛ پاسخ‌های «اکو» (متن مشابه خروجی اخیر در ۱۸۰ث) نادیده گرفته می‌شود؛ پاسخ تأخیری با `_schedule_deferred_auto_reply`.

### ۱.۴ عامل C — ویرایش فروشگاه (`_run_action_list` خط ۱۱۶۶)

برای هر نوبت: ۱) اگر `siteRevision` در این فاصله بالا رفته (ساخت تازه) رد می‌کند؛ ۲) snapshot کل فایل‌های قابل‌ویرایش (`.sozan-turn-<id>`)؛ ۳) هر اکشن به ترتیب: اجرا ← (در صورت لزوم publish به runtime) ← `verify_action` (روی دیسک و روی سایت زنده با HTTP) ← `record_trace`؛ ۴) اولین شکست: `_restore_and_republish`، `hidePrices` و `pendingBuild` برگردانده می‌شود و `break`. اکشن‌های وابسته (`depends_on: create_page:<kind>`) فقط اگر پیش‌نیازشان موفق بوده اجرا می‌شوند. بعد از موفقیت، snapshot به `.sozan-prev` منتقل می‌شود تا «برگرد» (undo یک‌مرحله‌ای) کار کند.

ساخت کامل (`shop_service.start_build`): `subprocess.run` اسکریپت کارخانه با `--detach`؛ حالت job با فایل‌های `queue/fastpath/jobs/<id>.json` رصد می‌شود؛ بیش از ۳۰ دقیقه بی‌حرکت ← `failed` (`JOB_STALE_SECONDS`). ساخت کامل فقط با «بساز/دوباره بساز» یا دکمهٔ بیلد؛ تغییرات معمولی `reviseOnly` هستند.

### ۱.۵ عامل D — استودیو

`studio_chat_service.chat` (خط ۱۱۸۱): سلام ← پاسخ ثابت؛ فقط هشتگ ← `_write_hashtags`؛ بازنویسی کپشن قبلی ← `_rewrite_existing`؛ وگرنه `_studio_json` با تا ۳ تلاش (retry کپشن ناقص، retry «بک‌استیج»، retry «کپشن کوتاه با نام کالا»)، سپس `_ensure_english_prompt`، سپس ساخت تصویر در `studio_compose_service._run` که در thread (`asyncio.to_thread`) اجرا می‌شود.
تصویر (`image_provider_service`): ابر اصلی ← یک retry بعد از ۴ثانیه ← fallback اختیاری (`IMAGE_FALLBACK=seedream|arvan`) ← محلی فقط پشت فلگ dev. **گارد بینایی:** بعد از تولید، یک مدل بینایی می‌پرسد «این گردنبند است؟» (`_ask_subject`) و برای ویرایش، «آیا هر دو تصویر همان کالا هستند؟» (`_ask_same`)؛ در رد، یک بار دوباره می‌سازد؛ دوباره رد ← `SUBJECT_FAIL`. این یک **حلقهٔ تولید/نقد/اصلاح** واقعی است، ولی تک‌دور.

### ۱.۶ عامل E — تلفن (`voice-gateway/main.py`)

`Gateway._converse` (خط ۸۳۵) حلقهٔ تماس است: سقف ۱۵ دقیقه؛ هر ۰٫۱۵ث از `session.utterances` می‌خواند؛ `gate_kind` (گفتار/نویز)؛ STT (محلی)؛ تشخیص پیام اپراتور (`is_carrier_text`)؛ حذف اکو و barge-in؛ سپس `_turn`:

- **حالت پشتیبانی:** زنجیرهٔ کوتاه‌شاخه‌ها (bye/repeat/hold/who/done/stuck/correction/howdy/hello/ack) ← `brain.understand` (شباهت بردار bge-m3 با ۱۰۰ جملهٔ فارسی-تلفنی در `meaning.py`، جملهٔ جواب **ثابت** است) ← فقط اگر امتیاز < ۰٫۶۲ و `worth_llm`: `brain.reply` با LLM.
- **حالت فروش:** `plan_turn` (ماشین حالت `SalesState`: `greet→discover→pitch→cta→confirm→close`) برمی‌گرداند یکی از `hold/hello/close/address/fallback/feature/model`. فقط `model` به LLM می‌رسد (`ornith-phone`، ۷۰ توکن، ۴ث تا اولین توکن وگرنه جملهٔ ثابت). همهٔ جملات بحرانی (سلام، خداحافظ، آدرس سایت، قیمت، اعتراض‌ها) **ثابت** هستند و مدل نمی‌سازد.
- پایان: `[پایان]` در خروجی مدل یا `hangup` در `TurnPlan`؛ «زنگ نزنید/اشتباه گرفتی» ← `remember_dnc(number)` در `~/local-ai/config/sozan-dnc.txt`.

## ۲) ابزارها (Tools)

### ۲.۱ ابزارهای روتر (`router_service.py:117-222`)

| ابزار | سطح (`_tool_level`) | رتبه | اثر |
|---|---|---|---|
| `status` | read | 3 | `_status_payload`: وضعیت فروشگاه/اسکن/بیلد/دامنه/کانال/پلن/کیف |
| `inbox_status` | read | 3 | خوانده‌نشده، حالت پاسخ خودکار، تعداد نخ |
| `ask_user` | read | 2 | سؤال ساخت‌یافته با حداکثر ۶ گزینه |
| `shop_chat` | read (passthrough) | 1 | چت/ساخت ویترین؛ «از نو» کارت می‌گیرد |
| `set_auto_reply` | **write** | 0 | `inbox_service.save_auto_reply` (enum: `""`,`draft`,`send`) |
| `set_voice_tone` | **write** | 0 | `voice_service.apply_tone` (warm/formal/street/luxury) |
| `edit_shop` | **write** | 0 | `apply_live_edit` با اکشن‌های `_MUTATIONS` |
| `add_product` | **write** | 0 | کاتالوگ + sync با سایت زنده |
| `studio_chat` | **write** | 0 | کپشن/پست/استوری؛ در حالت worker به صف می‌رود |
| `publish_post` | **write** | 0 | `studio_publish_service.publish` (تلگرام/واتساپ/دایرکت اینستاگرام) |

**نکتهٔ کلیدی:** schema بیشتر ابزارها `properties: {}` خالی است. مدل فقط **نام** را انتخاب می‌کند. آرگومان واقعی (قیمت، رنگ، متن جدید، پلتفرم) را کد از جملهٔ کاربر درمی‌آورد: `shop_intent_service.classify_actions` (regexهای فارسی، `_price_toman` با «میلیون/هزار/ت»)، `turn_parse.parse_turn` (داده‌محور از `router_registry.json`)، `_bind_recipient`، `_stamp_content_id`. نتیجه: مدل نمی‌تواند قیمت یا متن بسازد؛ فقط می‌تواند ابزار اشتباه انتخاب کند، که با «کارت تأیید» و `_authority_route` مهار می‌شود.

لایه‌های کنترل روی ابزار (به ترتیب اجرا):

1. `_never_tool`: regex `secret|jwt|api[_-]?key|otp|read_env|sql|token` روی نام ابزار.
2. `ALLOWED`: فهرست سفید (`WRITE ∪ PASSTHROUGH ∪ READ`).
3. `_reject_write`: اعتبارسنجی enum.
4. `_authority_route`: اصلاح انتخاب مدل با قاعده (مثلاً `edit_shop` بدون ویترین ← `shop_chat` با «اول بگو بساز»).
5. `_publish_block`: پلتفرم/مخاطب/پستِ آماده/پایان تصویر.
6. `HOLD_PENDING`: تا کارتِ باز تعیین‌تکلیف نشود هیچ ابزار نوشتنی دیگر اجرا نمی‌شود.
7. **کارت تأیید** برای همهٔ `WRITE_TOOLS`؛ اجرا فقط با `confirmId` برابر.
8. `_guard_reply` روی متن خروجی: نشت نام ابزار (`_TOOL_LEAK`)، رد انگلیسی، متن ممنوع.

### ۲.۲ ابزارهای دایرکت (`inbox_agent_service._tools` خط ۱۳۸)

`stock(product)` (موجودی/قیمت/رنگ/سایز واقعی از کاتالوگ)، `order_status(order_id)`، `payment_link(product, qty 1..5)`. `payment_link` فقط اگر `_explicit_buy(sentence)` باشد در فهرست می‌آید؛ حتی اگر مدل صدایش بزند و `allow_payment=False` باشد `{"ok": false}` برمی‌گردد. برای فروشندهٔ بدون درگاه شخصی، لینک «خشک» (`dry-mock.invalid`) ساخته می‌شود و رسید ثبت می‌شود؛ تأیید نهایی پرداخت با فروشنده است (`CONFIRM_LINE`).

### ۲.۳ اکشن‌های ویرایش فروشگاه (۱۵ نوع، `shop_route_service.EDIT_TYPES`)

`edit_llm`، `set_colors`، `set_brand`، `replace_text`، `delete_text`، `hero_image`، `add_product`، `remove_product`، `set_header`، `add_nav_link`، `create_page`، `hide_prices`، `show_prices`، `catalog_from_page`، `revert`.
هرکدام patcher مشخصی روی فایل‌های مشخص دارد (`lib/brand.ts`، `app/brand-vars.css`، `public/catalog.json`، `public/storefront-flags.json`، `lib/nav.ts`...). مدل کد TSX دلخواه نمی‌نویسد. حتی مسیر `edit_llm` فقط JSON اکشن می‌دهد (`_normalize_llm_actions`) و از همان patcher/verify می‌گذرد.

### ۲.۴ ابزارهای غیر LLM در دسترس عامل‌ها

کارخانهٔ سایت (`subprocess`)، DNS آروان، ارائه‌دهندهٔ تصویر + برش پس‌زمینه (`cloud_cutout_service`)، ffmpeg (`compose_pipeline`)، انتشار کانال‌ها، پرداخت (زرین‌پال/آیدی‌پی)، پیامک، اسکن کانال (`channel_scan_service`)، Sendbox/Unipile/Meta.

### ۲.۵ ابزارهای عامل تلفن

بدون tool-calling. «ابزار» همان توابع کد است: `price_spoken_line` (قیمت فقط از `GET /billing/plans` و به‌صورت گفتاری با `toman_words`)، `payment_ready` (`/health`)، `remember_dnc`، `gift_spoken_code`. LLM هیچ تابعی صدا نمی‌زند.

### ۲.۶ چیزهایی که **نیست**

- هیچ MCP/پلاگین زمان‌اجرا برای عامل‌های محصول وجود ندارد.
- `.zcode/skills/` و `.cursor/skills/` مهارت‌های ابزار کدنویسی توسعه‌دهنده‌اند (۴۴۷ فایل از ۱۱۴۳ فایل مخزن)، نه بخشی از عامل محصول.
- مدل ابزار اجرای کد، شل یا فایل دلخواه ندارد.

## ۴) محیط (Environment)

### ۴.۱ مرز مستأجر (tenant)

- `state_store._tenant`: `ContextVar`. `get_current_user` پس از JWT ← `set_tenant(user.phone)`؛ پس همهٔ `read_json/write_json` خودکار در `tenants/{phone}/` می‌روند. حلقه‌های پس‌زمینه با `tenant_scope(phone)`؛ worker با `tenant_scope(job.tenant)`.
- `iter_tenants` پوشهٔ `_none` را رد می‌کند؛ `set_tenant` شمارهٔ نامعتبر را رد می‌کند (جلوگیری از نوشتن در `_none`).
- نوشتن اتمیک: `mkstemp` در همان پوشه + `fsync` + `os.replace`. فایل خراب JSON ← پیش‌فرض + هشدار.
- قفل‌ها: `tenant_file_lock(name)` با `fcntl.flock` و **reentrancy** به‌ازای (thread, task, name)؛ `shared_lock` سراسری (RLock + flock) برای فایل‌های مشترک.
- حافظهٔ Chroma (اگر وصل شود): نام پایگاه‌داده `sha256("sozan-memory-v1\n"+phone)[:32]`، هرگز از ورودی کاربر/مدل.
- مرز در سطح **فایل/پوشه** است، نه پایگاه‌داده؛ نشت بین مستأجر یعنی خطای کد در انتخاب مسیر. تست‌های `tenant_lock_test`، `state_store_test` و `shop_memory_service_test` این مرز را می‌سنجند.

### ۴.۲ توپولوژی اجرا

| محل | اجزا |
|---|---|
| **هاب (ابر ایران)** | FastAPI (`127.0.0.1:8012`)، پنل Next (`3010`)، Postgres 16 (`15432`)، Redis 7 (`16379`)، nginx، `sozan-worker`، کانتینر هر فروشگاه (`12410+`)، تایمرهای battery/backup/dns-watch |
| **ماشین خانه** | llama-swap (`19292`)، observe (`9292`)، گیت‌وی OpenClaw (`18789`)، کارخانهٔ سایت (`site-builder`)، `sozan-voice` (SIP + `ornith-phone`)، monitor، nightly train |
| **ابر LLM** | OpenRouter/آروان: DeepSeek-V4-Pro (فروشگاه/روتر/کارخانه)، Gemini-3.1-Flash-Lite (استودیو)، Haiku→DeepSeek→qwen3.5-9b (دایرکت) |
| **اتصال** | تونل معکوس SSH `-R 9292`؛ SOCKS خانه برای پیام‌رسان‌ها؛ پراکسی npm؛ Tailscale برای Unipile |

انتخاب مدل (`llm.route_for_surface` خط ۳۲۴): `llm-routing.json` (override از observe) ← کارخانه/فروشگاه/روتر/دایرکت: ابر ← استودیو: ابر Gemini ← وگرنه محلی. روتر **بدون ابر کار نمی‌کند** (`router_requires_cloud`) مگر سقف هزینه خورده باشد.

### ۴.۳ رقابت روی GPU (`llm.py:464-517`)

`factory_holds_gpu1()` فایل‌های `queue/fastpath/ACTIVE` (pid زنده) و `queue/phase.json` (فاز GPU1 و تازه‌تر از ۱۵ دقیقه) را می‌خواند. `_ensure_gpu1` تا وقتی کارخانه GPU1 را دارد هیچ مدلی را unload نمی‌کند و به مدل ۲۷B لودشده یا `qwen3.5-9b` می‌افتد (`gpu1-busy`). مستند تلفن (`sozanvoice.md`) می‌گوید وقتی `ornith-phone` روی Vulkan1 باشد، پراکسی observe هر درخواست مدل بزرگ را به ۹B برمی‌گرداند و کنترل شماره‌گیری `busy` می‌دهد.

### ۴.۴ ایزولهٔ زیرپروسهٔ کارخانه

`shop_service._factory_env` (خط ۴۹۹): فقط کلیدهای `SOZAN_*`، `LLAMA_*` و `FACTORY_ENV_ALLOW`؛ رازهای هاب منتقل نمی‌شوند؛ پراکسی/ریجستری npm صریح؛ `SOZAN_PAY_SECRET` هر فروشگاه جدا. شروع با timeout ۴۰ث؛ ساخت `--detach`.

### ۴.۵ مجوز، سقف و هزینه

- **نقش/مجوز:** همهٔ کاربران `admin` با `campaigns:read|write|export`؛ «مدیر هاب» = `ADMIN_PHONE`.
- **سقف رفتاری:** روتر ۸۰ نوبت/روز و ۱۲٬۰۰۰ توکن؛ دایرکت ≤۲۰ ارسال خودکار/ساعت/نخ؛ برش پس‌زمینه ≤۳ هم‌زمان؛ OTP سقف سراسری.
- **سقف هزینهٔ ابری** (`ai_budget_service`): شرکت ۱۰ دلار/روز؛ هر پلن سقف روزانه/هفتگی (free ≈ 0٫۰۰۲، pro ≈ 0٫۱۵، promax ≈ 0٫۲۱، ultra ≈ 0٫۲۹ دلار/روز)؛ روز بر مبنای تهران UTC+3:30؛ هزینه از `usage.cost` هر پاسخ؛ پس از سقف همهٔ سطح‌ها (به‌جز `voice/phone`) محلی می‌شوند. خطا در محاسبهٔ بودجه ← ابر **باز می‌ماند** (fail-open؛ F9).
- **تکرارناپذیری:** `Idempotency-Key` + هش بدنه، ۲۴ساعت (`idempotency_service`)؛ کلید یکسان با بدنهٔ متفاوت ← `422`؛ فرانت کلید را تا پایان قطعی نگه می‌دارد (`lib/idempotency.ts`، خطای نامطمئن شبکه کلید را حفظ می‌کند).
- **سخت‌سازی:** `docs/openapi` خاموش؛ `X-Frame-Options: DENY`؛ `TRUSTED_IP_HEADER`؛ گارد شروع.

### ۴.۶ سندباکس

برای عامل‌های محصول **سندباکس اجرای کد لازم نشده** چون مدل کدی اجرا نمی‌کند. «محیط امن» همان فهرست سفید ابزار + patcherهای قطعی + کارت تأیید + rollback است.

### ۵.۴ حافظهٔ مشتری (`customer_memory_service`)

> **یافتهٔ F7 (مهم):** `answer()` فقط وقتی `source == "real"` حافظه را می‌نویسد، ولی در کد تولیدی تنها فراخوان‌های `answer` اینها هستند: `voice_service.draft_reply` با `source="voice"` (مسیر پاسخ خودکار صندوق) و `api/inbox.py` (`/inbox/dry-reply`) با `source="battery"`. هیچ فراخوانی با `"real"` وجود ندارد. پس طبق خواندن ایستا، **حافظهٔ مشتری در تولید هیچ‌وقت نوشته نمی‌شود و نمونهٔ آموزشی `inbox_reply` هم ثبت نمی‌شود** (`_log_train` برای `source=="voice"` برمی‌گردد). به نظر می‌رسد واژهٔ «voice» (که قرار بود یعنی «تلفن») با «پیش‌نویس خودکار» اشتباه شده است. (باید روی هاب با دادهٔ واقعی تأیید شود: وجود `customer-memory.json`.)

## ۶) مشاهده‌پذیری (Observability)

### ۶.۱ خط لولهٔ رویداد (`observe_client.py`)

1. `emit_later(kind, title, ...)` ← `envelope()` ← `_post_event` (`POST {observe}/sozan/events`، timeout ۰٫۸ث، `trust_env=False`).
2. در شکست: `observe-outbox.jsonl` (در پوشهٔ مستأجر؛ بدون مستأجر در ریشه) با `queuedAt` و `attempts`. `flush_outbox(limit=40)` بعد از هر `emit_later` اجرا می‌شود.
3. `emit_later` اگر event loop نباشد، یک **thread daemon با `asyncio.run`** باز می‌کند (به‌ازای هر رویداد).

**envelope:** `eventVersion`، `eventId`، `tenant`، `conversationId`، `turnId`، `operationId`، `jobId`، `scanId`، `parentId`، `surface`، `component`، `releaseId`، `behaviorVersion`، `stage`، `status`، `startedAt`، `durationMs`، `kind`، `title`(≤۲۴۰)، `brand`، `payload`.

`hub_release_id()` = هش ۲۰ نویسه‌ای از هش فایل‌های `observe_client`، `shop_service`، `shop_edit_service`، `channel_scan_service`، `shop_intent_service`، `shop_route_service` + اسکریپت کارخانه؛ `BEHAVIOR_VERSION="2026.09.16-pipeline"` ثابت دستی است (هش خودکار نیست).

### ۶.۲ همبستگی با درخواست مدل

هر درخواست LLM هدرهای `X-Sozan-Tenant/Surface/Brand/Release/Behavior/Request` دارد (مقدار غیر ASCII با percent-encode) و `X-Sozan-Route` (`default/override/fallback/inbox-fallback`). پراکسی observe می‌تواند درخواست خام را به رویداد اپ بچسباند.

### ۶.۳ سنجه‌های LLM

`_emit_usage`: توکن prompt/completion، مدل، provider، تأخیر، `usage.cost`. `_classify_llm_error`: `timeout`، `unreachable`، `half-closed`، `rate-limit`، `http-5xx`، `http-4xx`، `llm_unreachable`، `bad-json`. رویدادهای ویژه: `cloud-fallback`، `cloud-capped`، `gpu1-busy`، `routing-stale`، `provider-auth` (۴۰۱/۴۰۲، ساعتی)، `chat-failed`، `router-embed-fail/rescue`.

## ۸) پیشنهادهای اولویت‌دار

1. **(فوری، کم‌هزینه) رفع F7:** در `voice_service.draft_reply` منبع را `"real"` بگذارید و برای تلفن از مقدار جدا (مثل `"phone"`) استفاده شود؛ یا پارامتر مستقل `record=True`. بعد وجود `customer-memory.json` و نمونه‌های `inbox_reply` را روی هاب بررسی کنید. تست واحد بنویسید که `answer(..., source="real")` حافظه را می‌نویسد و `draft_reply` آن را فرا می‌خواند.
2. **قفل outbox (F1):** `tenant_file_lock("observe")` دور خواندن+بازنویسی یا جابه‌جایی به «rename-then-process» (فایل را اتمیک به `.processing` تغییر نام دهید، پردازش کنید، موارد ناموفق را append کنید). همزمان سقف تعداد (مثلاً ۲۰۰۰ خط) برای outbox.
3. **چرخش/سقف لاگ‌ها (F2):** `router-turns.jsonl` را مثل `trace.jsonl` به ۲۰۰–۵۰۰ ردیف محدود کنید یا روزانه rotate کنید.
4. **غیرهمگام‌کردن کارخانه (F5):** `_run_factory` را با `asyncio.to_thread` یا `asyncio.create_subprocess_exec` صدا بزنید؛ برای `status` فایل job را مستقیم بخوانید (`_read_job_file` همین‌الان وجود دارد) و فقط در نبودش به subprocess برگردید.
5. **CI (F10):** یک workflow ساده: `pip install -r backend/requirements.txt`، `python -m unittest discover`، و `npm run build` برای فرانت. تست‌های ناپایدار (F11) را با ایزولهٔ `OBSERVE`/نصب `onnxruntime` یا skip صریح بپوشانید.
6. **نسخهٔ رفتار خودکار (F12):** فهرست فایل‌های `_HUB_FILES` را به `router_service`، `llm`، `inbox_agent_service`، `studio_chat_service`، `turn_parse` و فایل‌های `data/*.json` گسترش دهید.
7. **تاریخچهٔ کوتاه برای روتر (F3):** افزودن ۲–۳ نوبت آخر (فقط متن کاربر و خلاصهٔ «ابزار اجراشده») بدون تغییر ساختار تک‌گذر؛ با ارزیابی روی `qa50`.
8. **وصل یا حذف Chroma (F6):** یا `search("policies"/"answers")` را به `_known_reply` دایرکت وصل کنید، یا در مستندات صریح بنویسید که فعلاً غیرفعال است؛ همین‌طور برای کد مرده (F8).
9. **سیاست متن فروشنده در observe (F14):** یا ماسک (`mask_pii`) و برش، یا بیان صریح در `docs/فنی.md`.
10. **برچسب‌های قوی روتر (F13):** ثبت «کارت لغو شد/تأیید شد» و «پیام اصلاحی بلافاصله بعد از نوبت» به‌عنوان `log_label`.
