# پژوهش جامع: چت واحد سوزان با مدل روتر — نسخهٔ ۱

**به قلم Z — ۲۱ سپتامبر ۲۰۲۶ — به فرمان مالک. این سند زنده است؛ هر سه نفر تیم (مالک، X، Z) باید بخش تحقیق خود را به آن بیفزایند. خروجی نهایی: پلن جامع در `talk.md`.**

---

## ۰. چکیده

سوزان از «چند صفحهٔ چت جدا» به **یک صفحهٔ چت واحد** تبدیل می‌شود که پس از AUTH مسیر پیش‌فرض است. یک **مدل روتر** (انتخاب مالک: `GPT-OSS-120B` روی آروان) گفتگو را می‌گیرد، تنظیمات و تغییرات درون اپ را خودش با «ابزار» اعمال می‌کند، تولید محتوا و برنامه‌نویسی را به مدل‌های دیگر واگذار می‌کند، و دایرکت همان‌طور که قفل شده روی GPU لوکال می‌ماند. ۴ تا ۶ ایجنت/کار پس‌زمینه (ساخت فروشگاه، تولید محتوا، کانال‌ها، دایرکت‌ها و…) پشت همین صفحه کار می‌کنند. روتر هرجا نامفهوم بود، خودش سؤال می‌پرسد. کلید API آروان از یک «باکس امن» به او می‌رسد و کارهای دامنه/CNAME را خودش انجام می‌دهد. منو به سایدبار می‌رود.

---

## ۱. خواسته‌های مالک — عیناً و شفاف

1. **یک صفحهٔ چت واحد** هم برای محتوا و هم برای ساخت فروشگاه.
2. **کنترل تمام امکانات سوزان از همان چت** — مثال‌های خود مالک: نحوهٔ پاسخ به دایرکت، ست کردن OTP، لحن دایرکت، مشورت برای پیشرفت کسب‌وکار.
3. **یک مدل روتر:** تغییرات درون اپ را خودش اعمال کند؛ تولید محتوا و برنامه‌نویسی را به بقیهٔ مدل‌ها بسپارد؛ دایرکت لوکال بماند (تصمیم قفل‌شدهٔ قبلی).
4. **روتر = `GPT-OSS-120B`** (نظر صریح مالک؛ همین امروز روی `ai.sozan-core.ir` زنده است).
5. **مسیر پیش‌فرض بعد از AUTH → صفحهٔ چت.**
6. **۴ تا ۶ کار/ایجنت پس‌زمینه** در صفحهٔ چت — مثال‌های مالک: ساخت فروشگاه، تولید محتوا، کانال‌ها، دایرکت‌ها و… .
7. **روتـر خودش سؤال بپرسد** هرجا خواسته نامفهوم بود.
8. **باکس امن برای کلید API آروانکلاد** — روتر کلید را از آنجا می‌گیرد و خودش دامنه و CNAME و امثال آن را ست می‌کند.
9. **منو به سایدبار منتقل شود.**

## ۲. کشف کلیدی این پژوهش — probe زندهٔ Z (۲۱ سپ)

`GPT-OSS-120B` روی Endpoint آروان **tool-calling استاندارد OpenAI را کامل پشتیبانی می‌کند.** تست واقعی:

- درخواست: «لحن پاسخ به دایرکت‌ها را صمیمی کن.» با یک ابزار `set_direct_tone(tone: formal|casual|friendly)` و `tool_choice: auto`
- پاسخ: `tool_calls: [{"function": {"name": "set_direct_tone", "arguments": "{\"tone\": \"friendly\"}"}}]` با `finish_reason: "tool_calls"`

**معنی معماری:** روتر لازم نیست «متنِ فرمان» تولید کند که جایی پارس شود — حلقهٔ استاندارد `tool_call → اجرا → tool_result → ادامهٔ گفتگو` مستقیم روی زیرساخت فعلی آروان کار می‌کند. این بزرگ‌ترین ریسک فنی طرح بود و بسته شد.

## ۴. فهرست کامل «هر امکان سوزان از چت» — جدول قابلیت‌ها

هر ردیف: گفتار نمونهٔ کاربر → زیرساخت امروز → وضعیت برای چت.

**الف) فروشگاه**
| گفتار نمونه | زیرساخت | وضعیت |
| --- | --- | --- |
| «فروشگاه لباس بزن پایه، سبک مینیمال، رنگ کرم» | shop_service.chat + factory build | چت هست، باید روتر بخوانَدش |
| «دکمهٔ خرید را زرشکی کن» (ادیت صفحه) | shop_edit_service + publish runtime | ✓ |
| «قیمت‌ها را مخفی کن، فقط استعلام» | hidePrices | ✓ |
| «سایت را بازسازی کن / فقط همین صفحه را عوض کن» | rebuild/revise | ✓ |
| «فروشگاه را زنده کن» | زنده = بیلد `ready` + دامنه (`PATCH /shop/domain` + CNAME) — نیتِ جدا نیست | ✓ |

**ب) انبار و کالا**
| «این ۵ کالا را اضافه کن…»، «عکس‌های کم را بگذار»، «کالای بی‌قیمت‌ها را لیست کن» | inventory/catalog + scan | ✓ |

**ج) محتوا و انتشار**
| «برای این پست کپشن بنویس»، «این را در کانال تلگرام بفرست»، «به دایرکت اینستا به [مخاطب] بگو که…» | studio_compose تکی + کمپین جدا؛ انتشار: TG یک‌ضرب، IG **دایرکت به مخاطب** (فید نیست)، WA هم هست | ✓ — روتر به‌جای کارگرِ متن، delegate می‌کند |

**د) کانال‌ها**
| «تلگرامم را وصل کن»، «پیج اینستا را با ورود رسمی وصل کن»، «وضعیت اتصال‌ها؟» | channels API (BoxAPI رسمی، TG bot، WA) | ✓ |

**هـ) صندوق و دایرکت**
| «خوانده‌نشده‌ها؟»، «این گفتگو را خودت جواب بده با لحن صمیمی»، «پاسخ خودکار را پیش‌نویس/ارسال/خاموش کن» | inbox-settings (`autoReply`: ""/draft/send از `PATCH /inbox/settings` — **هست**)؛ لحن از `voice.json` (ابزار روتر می‌سازد) | پاسخ‌گویی همان مسیر لوکال |

**و) تنظیمات و امنیت (خواستهٔ صریح مالک)**
| «OTP تستی را فعال کن با این شماره‌ها»، «TTL پیامک را ۵ دقیقه بگذار»، «لحن دایرکت را رسمی کن» | settings + otp-fixed (در راه) | گارد هاب B0 باید دور ابزارهای write بماند |
| «مدل چت را عوض کن»، «توکن آروان را عوض کن» | llm routing + باکس امن | حساس — با تأیید |

**ز) دامنه و DNS (خواستهٔ ۸)**
| «کلید آروان این است؛ دامنهٔ shop.com را وصل کن» | arvan_dns_service + CNAME + nginx map اتمیک | هست؛ باکس امن + دست روتر لازم است |

**ح) پول**
| «شارژ کیف چقدر شد؟»، «تراکنش‌های این هفته؟» | pay/wallet | فقط-خواندنی برای روتر؛ پرداخت با تأیید |

**ط) داده و مشاوره (خواستهٔ صریح مالک)**
| «مغازه‌ام چطور پیش برود؟»، «کدام کپشن بهتر جواب داد؟» | دادهٔ واقعی: وضعیت فروشگاه، اسکن بی‌قیمت/بی‌عکس، unread، پلن؛ `copy_variants` ذخیره است ولی **گزارش digest نیست** | **بخش جدید**: digest کوتاه عددی، نه نثر انگیزشی |

**ی) حساب و صفحات**
| «خارج شو» | auth | تغییر شماره **API ندارد** (خروج سمت کلاینت) — اگر خواسته شود، ساخت جدید |

## ۵. معماری پیشنهادی Z (پیش‌نویس برای بحث — نه تصمیم نهایی)

1. **روتر در `sozan-api`:** یک سرویس `router_service` با حلقهٔ tool-calling روی `GPT-OSS-120B@ai` (همان کلاینت/proxy/fallback امروزی). ابزارها = پوشش‌های نازکِ امن روی سرویس‌های موجود؛ هیچ دسترسی مستقیم DB.
2. **سه سطح اتوریتی برای ابزارها:**
   - **read-only** (گزارش‌ها، وضعیت‌ها) → اجرای بی‌تأیید
   - **write معمولی** (ادیت سایت، کپشن، افزودن کالا) → خلاصهٔ عمل + دکمهٔ تأیید در چت
   - **حساس** (OTP، دامنه/DNS، پول، تغییر مدل/توکن) → تأیید صریح + رکورد audit در observe
3. **Delegation به جای انجام:** روتر برای متن/کد، ابزار `delegate` را صدا می‌زند (surface مشخص: studio/factory/image) — یعنی همان `route_for_surface` امروزی، سومی می‌شود: کاربر → روتر → کارگرِ درست.
4. **کارهای پس‌زمینه:** همان job-های امروز (build، compose، publish) با پنل تسک در UI چت؛ وضعیت هر تسک رویداد observe → استریم به صفحه. شروع با همین ۵-۶ تا: ساخت فروشگاه، تولید محتوا، انتشار، دایرکت/صندوق، دامنه، تحلیل هفتگی.
5. **نامفهومی → ابزار `ask_user`:** روتر به‌جای حدس زدن، سؤال ساخت‌یافته با گزینه‌ها می‌فرستد (خواستهٔ ۷).
6. **باکس امن (خواستهٔ ۸):** فرم جدا و masked برای کلیدها در UI؛ ذخیره در env/فایل 600؛ **هرگز** وارد تاریخچهٔ چت و پرامپت روتر نمی‌شود؛ روتر فقط «نوع عمل» را می‌بیند نه خود کلید را.
7. **گزینهٔ جدی برای بحث — میزبان روتر روی گیت‌وی:** فورک OpenClaw همین حالا روی هاب `sozan-gateway` است؛ می‌تواند میزبانِ عاملِ روتر/کدنویس باشد (ابزار، حافظه، صف داخلی دارد). تصمیم: روتر در api یا گیت‌وی؟ (سؤال ۷.۲)
8. **UI:** `/chat` پیش‌فرض پس از AUTH؛ سایدبار منو (خواستهٔ ۹)؛ پنل تسک‌های پس‌زمینه؛ استریم پاسخ.
9. **هزینه و سقف:** هر پیام روتر ≥ ۲ کال مدل (تفسیر + ابزار). Rate-limit آروان ۱۲۰/دقیقه مشترک با فروشگاه — پایش observe + سقف per-tenant.

## ۷. سؤال‌های تحقیق — هر سه نفر پاسخ دهند (بخش پاسخ با امضای خودتان به همین فایل اضافه کنید)

1. **حافظهٔ روتر:** گفتگوهای قبلی هر tenant کجا بماند؟ (همان پیام‌های امروز کافی است؟ خلاصهٔ کاربر/برند لازم؟)
2. **میزبان روتر:** داخل `sozan-api` (ساده، هم-tenant) یا روی گیت‌وی OpenClaw (قدتمند، ولی مرز tenancy/احراز جداست)؟
3. **مرز اتوریتی:** دقیقاً کدام ابزارها بدون تأیید؟ جدول کامل بسازیم.
4. **UX تأیید:** دکمهٔ در-چت کافی است یا برای حساس‌ها رمز دوم؟
5. **هزینه:** سقف پیام روتر per tenant per روز؟ رفتار وقتی سقف آروان (۱۲۰/دق) پر شد؟
6. **خطای ابزار:** اگر ابزار شکست خورد روتر چه کند — retry، سؤال، یا گزارش خطای فارسی؟
7. **تست‌پذیری:** هر ابزار = تست واحد؛ حلقهٔ روتر = تست یکپارچه با مدل mock. DoD چه باشد؟
8. **مهاجرت سه صفحه:** `/chat` جای هر سه برود یا سه صفحه موازی یک دورهٔ انتقال بمانند؟
9. **دایرکت:** روتر صندوق را «مدیریت» می‌کند (سیاست/لحن/گزارش) ولی «پاسخ‌گویی» لوکال — مرز دقیق کجاست؟
10. **باکس امن:** چه کلیدهایی؟ فقط آروان یا همه؟ چه کسی می‌بیند (فقط مالک tenant یا ادمین هاب هم)؟
11. **مشاورهٔ کسب‌وکار:** منبع داده = observe + فروش + A/B؛ خروجی اولیه چه شکلی باشد تا واقعی و نه کلیشه؟
12. **زبان و لحن روتر:** فارسی محاوره‌ای؟ ساده برای کاربر غیرفنی؟
13. **i18n بعدی:** فقط فارسی شروع؟
14. **اولویت MVP:** کوچک‌ترین چت-روترِ مفید چیست؟ (پیشنهاد Z: تنظیمات+وضعیت‌ها اول، ساخت فروشگاه آخر)

## ۸. نقشهٔ راه پیشنهادی (پیش‌نویس فازها — در پلن جامع نهایی می‌شود)

### موضع معماری (سؤال ۷.۲) — قاطع

**روتر باید داخل `sozan-api` باشد، نه روی `sozan-gateway`.**

گیت‌وی هاب الان عاملِ کارخانه است: bind لوکال، `auth: none`، بدون JWT/tenant، state مشترک ubuntu، دوازده پلاگین OpenClaw نه سرویس‌های سوزان. G0.5 فقط cutover آدرس کارخانه است، نه تبدیل گیت‌وی به چت محصول.

اگر روتر روی گیت‌وی بنشیند: tenancy می‌شکند، گارد B0 تنظیمات هاب دور می‌خورد، کلیدها و تاریخچهٔ چند فروشنده قاطی می‌شود، و Clean Architecture (API → Service → Repository) نقض می‌شود.

کار درست: سرویس `router_service` با حلقهٔ استاندارد `tool_call → سرویس موجود → tool_result`. ابزار = پوشش نازک روی همان API/سرویس امروز. گیت‌وی فقط **کارگر** می‌ماند (`delegate` به factory)، مثل امروز.

`complete_json` / `_chat_completion` امروز tools ندارند. حلقهٔ روتر سطح LLM جدید می‌خواهد (`surface=router`، OSS-120B روی `ai`، timeout مثل ابر، fallback لوکال **برای حلقهٔ ابزار ممنوع** — مدل ۹ب ابزار را حدس می‌زند).

### کاستی‌های جدول بخش ۴ نسبت به کد

گزارش کامل‌تر پایین؛ خلاصهٔ غلط‌های جدول:

| ردیف جدول | واقعیت کد |
| --- | --- |
| «ساعات کاری پاسخ خودکار» | **نیست.** فقط `autoReply` = `""` / `draft` / `send` در `inbox-settings.json` + سقف پلن |
| «سیاست/لحن = تنظیم جدید لازم» | سیاست autoReply **هست** (`PATCH /inbox/settings`). لحن از `voice.json` / onboard است، نه settings |
| «شماره‌ام را عوض کن ✓» | **نیست.** API تغییر شماره نداریم. خروج = `clearToken` سمت کلاینت، بدون `POST /auth/logout` |
| «otp-fixed در راه» + «گارد B0 باید بماند» | B0 **زده شده** (`STUDIO_KEYS` فقط ادمین هاب). OTP ثابت هنوز stash است، روی `main` نیست |
| «go-live» به‌عنوان یک نیت | نیت نام‌گذاری‌شده نیست؛ زنده = بیلد `ready` + دامنه/`PATCH /shop/domain` |
| «۵ کپشن این هفته» | ابزار تقویم محتوا نیست؛ استودیو چت تکی + کمپین جدا |
| انتشار اینستا | **دایرکت به مخاطب** است نه فید؛ واتساپ هم هست |
| مشاوره observe/A/B | `copy_variants` ذخیره است نه گزارش. API digest هفتگی **نیست** |
| باکس امن کلید آروان tenant | امروز `ARVAN_*` **هاب‌گلوبال** است؛ فرم masked برای کلید مستأجر وجود ندارد |

صفحات اول‌کلاس که جدول نیاورده و باید چت‌پذیر یا حداقل سایدبار بمانند: `/onboard`، `/brand`، `/campaigns`، `/sales`، `/more/wallet` (برداشت IBAN)، `/more/settings` (درگاه/پیامک)، docs.

پیش‌فرض بعد از AUTH امروز `/shop` است (`panel-home.tsx`)، نه `/chat`.

### پاسخ سؤال‌های بخش ۷

**۱. حافظه.** امروز سه انبار جدا: `shop-messages.json` (سقف حدود ۸۰)، `studio-messages.json`، `inbox.json`. برای MVP یک فایل tenant مثل `router-messages.json` + ۱۲ نوبت آخر در پرامپت (همان `visible_chat_turns`) کافی است. خلاصهٔ برند/لحن از `shop.json` + `voice.json` + onboard — جدول جدا نساز. کلید و توکن هرگز در تاریخچه نرود (امروز هم URL/هگز بلند از پرامپت چت حذف می‌شود).

**۲. میزبان.** `sozan-api`. گیت‌وی = delegate کارخانه فقط. بالا استدلال شد.

**۳. مرز اتوریتی (پیشنهاد اجرایی برای قفل Z):**

- **بدون تأیید (read):** وضعیت فروشگاه/اسکن، لیست کانال بدون راز، unread، پلن، ماندهٔ کیف (`available` نه شبا)، `cnameOk`.
- **تأیید در چت (write معمولی):** ادیت زنده فروشگاه (intentهای موجود: رنگ، متن، hidePrices، کالا…)، شروع compose استودیو، `autoReply`، لحن `voice`، pause ترد، افزودن کالای کاتالوگ.
- **تأیید صریح + audit observe (حساس):** دامنه/DNS، کلید پرداخت/پیامک مستأجر، برداشت کیف، پلن، `STUDIO_KEYS` هاب، تعویض مدل/توکن ابر، OTP ثابت.
- **هرگز از چت:** خواندن/نوشتن `JWT_SECRET`، `ARVAN_API_KEY` هاب، توکن LLM، فایل مستأجر دیگر، SQL/JSON خام.

گارد B0 روی ابزارهای `STUDIO_KEYS` همان `_is_hub_admin` بماند.

**۴. UX تأیید.** دکمهٔ در-چت برای write معمولی کافی است. حساس = همان دکمه + متن دقیق جهش (نه رمز دوم در MVP؛ ورود همین حالا OTP است). رمز دوم فقط اگر مالک برای پول/DNS اصرار کند.

**۵. هزینه.** سقف per-tenant per-روز در observe. پر شدن ۱۲۰/دقیقهٔ آروان: صف کوتاه + پیام فارسی «کمی صبر»؛ **fallback لوکال برای روتر نه.** فروشگاه/استودیو کارگر می‌توانند fallback بمانند.

**۶. خطای ابزار.** نتیجهٔ ساخت‌یافته به مدل (یک retry فقط برای خطای شبکه/timeout). بعد `ask_user` با خطای فارسی فروشنده‌فهم. DNS/پول/OTP retry خودکار ندارند. شکست کارگر delegate = وضعیت تسک failed در پنل، نه حلقهٔ بی‌پایان روتر.

**۷. تست.** هر ابزار = تست واحد با `tenant_scope` و بدون شبکه. حلقهٔ روتر = تست یکپارچه با LLM mock (`tool_calls` ساختگی). DoD فاز: روت فقط سرویس را صدا می‌زند؛ راز در payload observe نیست؛ write بدون confirm در تست رد می‌شود؛ inbox/voice در تستِ روتر به ابر نمی‌روند.

**۸. مهاجرت سه صفحه.** R1: `/chat` پیش‌فرض بعد از AUTH (جای `/shop` در `panel-home`). `/shop` و `/studio` و `/inbox` **موازی می‌مانند** تا R3 — سایدبار به آن‌ها لینک می‌دهد. حذف سه صفحه در یک اسپرینت پرخطر است (بیلد زنده، مخاطب IG، pause ترد).

**۹. مرز دایرکت.** روتر **مدیر** است نه پاسخ‌گو: unread، فیلتر، pause، `autoReply`، لحن voice. تولید متن پاسخ و ارسال = همان `voice_service` / `inbox_service.reply` با `surface=inbox|voice` روی GPU لوکال. روتر `complete_*` با این دو سطح را به ابر نفرستد و خودش پیام مشتری را cloud-complete نکند.

**۱۰. باکس امن.** دو طبقه جدا شود وگرنه قاطی می‌شود: (الف) کلیدهای **هاب** (`ARVAN_*`، LLM) — فقط ادمین هاب، B0، هرگز در چت؛ (ب) کلیدهای **مستأجر** (پیامک/درگاه در `integrations.json`) — masked در UI، روتر فقط «ست شد/نشد» می‌بیند. «کلید آروان مستأجر برای دامنهٔ شخصی» امروز در کد نیست؛ اگر مالک می‌خواهد، محصول جدید است نه reuse همان env هاب.

**۱۱. مشاوره.** بدون API جدید، دادهٔ واقعی داریم: وضعیت فروشگاه، اسکن بی‌قیمت/بی‌عکس، unread، پلن. MVP مشاوره = همین اعداد در یک digest کوتاه، نه نثر انگیزشی. A/B کپشن UI ندارد.

**۱۲. زبان.** فارسی محاوره‌ای ساده؛ قانون محصول همین است. روتر انگلیسی/JSON خام به UI ندهد.

**۱۳. i18n.** فقط فارسی.

**۱۴. MVP.** موافق پیش‌نویس Z: R1 خواندنی + `ask_user` + دو write کم‌خطر (`autoReply`، لحن). ساخت فروشگاه/کارخانه **آخر** — قفل GPU1 و job طولانی را در اسکلت چت نگذار. باکس امن و DNS = R4.

### کارهای پس‌زمینه (خواست ۶ مالک)

از روی jobهای موجود، نه ایجنت خیالی: (۱) بیلد/revise کارخانه (۲) اسکن کانال (۳) compose استودیو (۴) انتشار (۵) همگام صندوق (۶) CNAME check. پنل تسک = وضعیت همین‌ها روی observe، نه ران‌تایم چهارم.

### آنچه در R0 نباید قاطی شود

- OTP ثابت دستور جدا و goشده است؛ به این طرح وصلش نکنیم.
- وایر تصویر Flash-Image و G0.5 cutover هم go جدا می‌خواهند.
- تا پلن در `talk.md` قفل نشود کد روتر نمی‌زنم.

## پاسخ Z — پذیرش اصلاحات و قفل اولیه (۲۱ سپ)

سه ادعای اصلاحی X را در کد راستی‌آزمایی کردم و درست بودند: `autoReply` فقط حالتِ ""/draft/send است (ساعات کاری نیست)، پیش‌فرض بعد از AUTH الان `/shop`/`/onboard` است (`panel-home.tsx`)، و API تغییر شماره وجود ندارد. جدول بخش ۴ با همین اصلاحات به‌روز شد (ردیف‌های هـ، ی + دو ردیف مکمل، الف-آخر، ج، ط).

**مواضع X که پذیرفتم و مبنای پلن جامع می‌شوند:**
1. روتر در `sozan-api` (`router_service`)، گیت‌وی فقط کارگر کارخانه — استدلال tenancy/گارد B0 درست است.
2. fallback لوکال برای حلقهٔ ابزارِ روتر **ممنوع** (کارگرها می‌مانند).
3. مهاجرت: `/chat` پیش‌فرض از R1، سه صفحهٔ فعلی موازی تا R3.
4. باکس امن دوطبقه: کلیدهای هاب فقط ادمین (هرگز در چت)، کلیدهای مستأجر masked در `integrations.json`.
5. کارهای پس‌زمینه = همان شش job موجود؛ پنل تسک روی observe.
6. MVP (R1): ابزارهای خواندنی + `ask_user` + دو write کم‌خطر (`autoReply`، لحن)؛ کارخانه آخر؛ باکس امن/DNS = R4.
7. سطح‌بندی اتوریتی پیشنهادی X (بدون‌تأیید / تأیید در-چت / حساس+audit / هرگز) مبنای جدول قفل پلن.

**باقی‌مانده تا قفل پلن در talk:** فقط پاسخ‌های محصولی مالک — چهار سؤال: (۳) تأیید جدول اتوریتی، (۴) دکمهٔ در-چت کافی است یا رمز دوم برای پول/DNS، (۱۰) کلید آروانِ «مستأجر برای دامنهٔ شخصی» محصول جدید است — می‌خواهی یا نه، (۱۴) تأیید ترتیب MVP.
